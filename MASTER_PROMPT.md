## ЖЁСТКИЕ ОГРАНИЧЕНИЯ ИЗ ЗАДАНИЯ
- UI = HTML + CSS + JavaScript, структура пригодна для HTML web resource в Dynamics 365 (статический бандл, без SSR, API base настраивается).
- Модель, бэкенд, хранилище — на выбор. Без регистрации/логина.
- Чек-лист редактируется через UI: критерии, формулировки, вес, тип ответа (Да/Нет, шкала), доступность N/A, шкала. **Промпт оценки генерируется из конфигурации чек-листа**, а не из кода — на контроле заменят один критерий.
- Оценивается только **оператор**. Реплики `bot` и `system` — контекст.
- Языки RU / KZ / EN.
- Для каждого критерия: ответ, баллы, вес, объяснение, реплика-доказательство (кликабельная ссылка на сообщение/фрагмент звонка). Пропущенное действие → указать проверенный участок. N/A → причина.
- Расчёт итога строго по чек-листу: шкала → пропорционально весу; N/A → вес перераспределяется; итог округляется до 2 знаков; нет применимых → итог не считается; грубая ошибка отмечается отдельно.
- Апелляция: выбрать критерий + комментарий → проверяющий видит спорную оценку, комментарий и фрагмент → подтверждает/меняет + причина → пересчёт. В карточке: исходная оценка, решение, финал.
- Звонки: плеер / переход к записи по `audio_url`.
- Платная модель → указать название и стоимость одной оценки (все вызовы).
- До T+24: публичный Git-репозиторий + README с шагами запуска.

## ПРИНЦИПЫ АРХИТЕКТУРЫ (для точности)
- **LLM не считает баллы.** LLM возвращает по каждому критерию: `answer` (yes/no/na или ступень шкалы), `evidence` (индексы реплик), `reason`. Итог считает детерминированный код с юнит-тестами.
- Строгий JSON (structured output / tool schema), temperature 0. Валидация: ступень ∈ разрешённым, N/A только где разрешён, индексы реплик существуют и принадлежат нужному спикеру.
- Транскрипт подаётся с индексами `[#12 operator 01:15] текст` — модель ссылается на номера, а не цитирует.
- Правила-подсказки для однозначных случаев (детерминированные проверки как «вторая пара глаз»): первая реплика оператора, наличие системного «чат закрыт», и т.п. Конфликт правила и LLM → показываем флаг «требует проверки».
- Опционально для точности: self-consistency (N прогонов, голосование) по спорным критериям.
- Провайдер модели — за одним интерфейсом (облако + локальная через Ollama/OpenAI-совместимый endpoint).
- CORS: данные организаторов тянем только через свой бэкенд.

## ПРАВИЛА ДОКУМЕНТАЦИИ (Obsidian)
- Хранилище — папка `docs/` (открывается в Obsidian как vault). Начало — `docs/00 Home.md`.
- Связи — только wiki-ссылками `[[Заметка]]`, `[[Заметка#Заголовок]]`.
- У каждой заметки frontmatter: `tags`, `status` (draft/active/done), `updated`.
- Важное — callout'ами: `> [!warning]`, `> [!important]`, `> [!question]`.
- Решения — ADR-формат (контекст → решение → альтернативы → последствия), по шаблону `docs/templates/ADR.md`.
- Эксперименты точности — по шаблону `docs/templates/Эксперимент.md`.
- Документация обновляется в том же шаге, что и код. Не пишем воду — только то, что поможет в защите или в отладке.
